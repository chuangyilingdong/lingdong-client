# 平台侧改动清单：VibeCoding「发送次数」计数虚高（2026-09-25）

> 本文件是**给平台仓（`E:\学习平台正常`）的改动清单**，不是平台仓里的文件。
> 客户端仓这边不动平台代码（平台仓只读）；这里给出现象、证据、根因与两档补丁方案。

## 1 现象（学生实机，2026-09-25）

- 学生这节课**只按了 2 次发送**，客户端角标直接显示「使用次数 8/8」，而且**任务还在跑**（图1）。
- `8/8` 之后客户端 `.2.4` 起的禁用逻辑会把发送按钮锁死（`used >= limit` 直接禁用 + 拦 Enter）。
- 这节课的 `sendLimit` 是 8，平台 `session_students.vibecoding_sends` 已经写到 8。
- 客户端只是**显示**平台给的数：`%APPDATA%\@deepseek-ai\dsh-desktop\lingdong-classroom.json` 里
  `"sends": { "limit": 8, "used": 8, "remaining": 0 }`，来源是 `GET /api/student/runtime/client-context`。

## 2 证据：DSH 自己只认到 2 次真人发送

同一台机器 `dsh-home/storages/session_projcache/sessions/*.json`（DSH 的会话投影）：

| 会话 | turns | steps | 说明 |
|---|---|---|---|
| `session-abbbdacb…`（科技炫酷风格班级主页网站） | 1 | 225 | 1 轮 |
| `session-edf47ffb…`（科技风班级主页网站） | 1 | 24 | 1 轮 |

两个会话各 1 轮 = **2 次真人发送**。平台却记到 8。差额 6 = 每次发送多算 3。

## 3 根因：网关按「历史里的 user 消息条数」计数，`0.1.7` 的注入块没被减掉

`apps/server/src/services/vibecodingLessonSettings.js`：

- `countUserMessages(messages)`：数 `role === 'user'` 的条数（单调最大值 `seen`）；
- `isInjectedReminder(message)`：扣掉 dsh 注入的块 —— 只认两种形态：
  1. 以 `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.` 开头；
  2. 整条被 `<system-reminder> … </system-reminder>` 裹住（`agent-instructions`）。
- 该文件**自己的注释**就写着：「不减掉它，按一次发送会被记成 3 次」（2026-09-19 实测）。

现在的问题：**我们钉的 DSH 是 `0.1.7-alpha.2`**，它一轮请求里注入的 user 角色内容比 2026-09-19 那版
更多（技能/插件上下文、运行上下文刷新等），上面两条判据认不全 → 每按 1 次发送，历史里多出
`1（学生）+ N（注入）` 条 user 消息 → 6 次虚高 / 2 次真实发送 = N 约 3。
（图1 里「任务还在跑就已经 8/8」也说明它在**同一轮的多次请求**里持续累加。）

## 4 建议改动（两档，任选其一即可先止血）

### 方案 A（推荐，最小、最稳）：把「每次请求的增长」夹到 1

真人不可能在**同一个请求**里按两次发送：相邻两次网关请求之间，`seen` 最多只能 +1（多轮工具调用
复用的历史里，学生那条只出现一次）。所以对 `observed` 做一次夹取即可免疫任何注入膨胀：

```js
// services/vibecodingLessonSettings.js  → enforceVibecodingSendLimit()
const observed = countUserMessages(messages);
const seenBefore = await vibecodingSendUsage({ sessionId, studentId });
// 真人一次请求最多新增一条「学生发的」消息：注入块无论多少都压不出这个上限。
const bounded = Math.min(observed, seenBefore + 1);
const seen = Math.max(seenBefore, bounded);
```

- 好处：不需要认识每一种注入形态，新插件/新版本注入多少都不影响；
- 代价：如果**真出现**一条请求里带 2 条真人消息（现在不存在：发送按钮一次只发一条），会少算 1 次 —— 对学生有利的方向；
- 注意：`used` 仍按 `min(seen, limit)` 对外报，`used ≤ limit` 不变量不变。

### 方案 B（治本）：让判据认识 `0.1.7` 的注入形态

1. **先加一行诊断日志**（一次就能锁定是哪几块，别猜）：
   ```js
   for (const m of messages.filter(x => x?.role === 'user')) {
     const text = typeof m.content === 'string' ? m.content : JSON.stringify(m.content);
     if (!m.tool_call_id && !isInjectedReminder(m)) console.log('[sendlimit] user msg', text.slice(0, 80), text.length);
   }
   ```
   用我们客户端的这次真实会话说一次，日志里多出来的那几条就是要补的形态。
2. 按日志补进 `isInjectedReminder`（形态通常是「整条是某个固定前缀的模板」或「整条被某个标签裹住」）。
3. 长期看更该让**宿主**给出可判别的信号（`source.kind === 'user'` 在网关拿不到，因为网关只看到
   `{role, content}`）——要么网关透传一个「这条是真人输入的」标记，要么平台侧改用我们客户端上报的
   轮次（**不建议**：那份注释明确写了「不能信客户端报数」）。

## 5 现场影响与救急

- 已经 `used = limit` 的课堂：学生**按不了发送**（客户端禁用 + 平台 429 双保险）。
  救急只需老师在平台上把该课时的 `sendLimit` 调大或清空（清空 = 不设上限），或重开一次课堂。
- 计数只增不减（`seen` 单调），**调大上限后不会再虚增**：修正判据后，历史里的 `vibecoding_sends`
  仍是那个虚高的数，建议顺手把这节课的 `vibecoding_sends` 重置为 0（或 `limit` 之内）。

## 6 客户端侧关联改动（已做，供平台侧参考）

- 客户端**不做**本地计数、不自己加一，只显示 `client-context.sends`（`deploy/desktop/client-patch/lingdong-send-state.ts`）。
- `.2.4` 起 `used >= limit` 时禁用发送按钮并拦 Enter，避免学生按到第 N+1 次才吃 429；
  **真正的门禁仍在平台**（网关 429 是唯一权威）。

## 7 平台侧回复与落地（2026-09-26，**平台已修**）

平台侧确认了上面的根因，并按「补判据 + 夹取」两路一起修完（他们的口径）：

1. **补判据**：除原有的两种形态外，又认了时间快照、compaction 检查点与压缩请求、切模型通知、
   重复工具调用提醒、上下文清零态，以及起标题请求（原来「有意不排」的那个）。
2. **夹取（治本）**：同一个请求里真人最多只能 +1，所以 `seen` 每次最多推进 1 ——
   对**还没见过的新注入形态也免疫**，同时是对学生有利的方向（与本文档方案 A 一致）。
3. **工具轮不推计数**：请求末尾不是「像学生发的那条」就一点都不推 —— 学生反馈里
   「任务还在跑就已经 8/8」正是这条没管住。
4. **诊断**：认不出来的注入会打一行告警（内容前 80 字），下次客户端升级注入新块，
   看一眼 `journalctl` 就能定位是哪种形态。

对客户端的影响：

- 客户端侧**不需要改**：它只显示 `client-context.sends`、不做本地计数（`.2.4` 起的发送禁用
  逻辑照旧以平台数为准，平台修正后角标与禁用都会跟着正确）。
- ⚠️ 仍然建议平台顺手处理**已经虚高的存量**：`session_students.vibecoding_sends` 是单调值，
  判据修正后历史里的那个数不会自己降下来；已经 `used >= limit` 的课堂若不重置，
  学生这节课仍然发不出去（救急口径见 §5）。
