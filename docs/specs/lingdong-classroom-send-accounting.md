# 灵动 ai 课堂发送次数幂等计算

## 背景

课堂发送上限是教学控制，不是模型请求次数上限。一次学生发送会让 Agent 在后台产生多次模型请求
（工具轮、压缩、重试）；平台当前按对话历史里的 `user` 消息推断发送次数，遇到新的注入形态时会
把内部轮次误记为学生发送。2026-11-01 的实际课堂中，学生只发出少量消息，却产生了 146 次模型
请求并把 7 次上限耗尽。

## 产品规则

1. 一次用户点击发送产生一个稳定 `sendId`；同一轮 Agent 的所有模型请求必须携带同一个
   `x-zcode-send-id` 请求头。
2. 工具轮、压缩、标题、子代理、SSE 重试、网络重连和进程恢复都属于同一 `sendId`，不得增加次数。
3. 学生再次点击发送才生成新的 `sendId`。
4. 没有 `sendId` 的模型请求（标题 sidecar、非用户后台任务、旧客户端）不按新发送计数。
5. 平台数据库是发送次数的唯一权威；客户端本地 quota ledger 只是投影，必须向平台值单调收敛。
6. 客户端每 5 秒成功取得 `client-context` 时必须同步最新 `sends`，不能只在运行时 key 临近过期时同步。
7. 平台返回 `SEND_QUOTA_EXCEEDED` 时，客户端必须立即显示服务端结果并停止继续提交。

## 所有权

- 平台数据库拥有 `session_students` 的发送计数及 `sendId` 幂等记录。
- Agent runtime 拥有当前轮次 `turnId`，并将其作为网络请求的 `x-zcode-send-id`。
- Desktop Main 拥有课堂上下文轮询和本地 quota ledger 投影。
- Renderer 只读取快照并显示 `used/limit`，不得自行推导扣次。

## 事件顺序

```text
学生点击发送
  → Agent turn 创建稳定 turnId/sendId
  → 每个模型请求携带 x-zcode-send-id: turnId
  → 平台按 (session, student, sendId) 幂等计数
  → 同 sendId 的工具轮/重试不增加 used

Main 每 5 秒 client-context
  → 原子同步 quota ledger
  → Renderer 快照显示平台 used/limit
```

## 平台配合边界

平台端最终应改为“不同 sendId 数量”计数，并用数据库唯一约束保证并发幂等。消息内容启发式只能作为
旧客户端兼容层，不能作为新客户端的事实源。字段、表约束和验收口径见
`docs/operations/给平台-课堂发送计数与全局提示词-20261101.md`。

## 失败语义

- `client-context` 暂时失败：保留上次平台值，不将本地计数回退。
- 本地 ledger 写失败：界面可暂时陈旧，但服务端仍可拒绝；不得放行额外模型请求。
- 同一 sendId 并发到达：平台只允许一次计数成功。
- 旧客户端缺少 sendId：按平台兼容策略处理，不得把内部请求重新按消息条数误计。

## 验收

1. 1 次发送触发 100 次工具模型请求，平台计数只增加 1。
2. 同一 sendId 的失败重试、重连和进程恢复不增加计数。
3. 新用户发送使用新 sendId，计数增加 1。
4. 平台 used 从 2 更新到 7 后，客户端下一次 5 秒轮询显示 7/7。
5. 平台返回 429 时，客户端显示服务端 `SEND_QUOTA_EXCEEDED`，且不继续发网关请求。
