# 灵动Code VibeCoding 短会话与工具执行策略

## 背景

课堂和学生端实测显示，VibeCoding 任务通常只有 2–3 个用户轮次，不需要按长上下文产品优化。当前慢请求同时受两类问题放大：

- `deepseek-flash` 新会话默认落到 `max` 思考档位，首 token 可等待 170–275 秒。
- `ApplyPatch` 实现存在但未注册，模型只能连续调用 `Edit`，一次任务可产生数百次模型与工具往返。

## 产品规则

1. **思考档位**
   - `deepseek-flash` 的合法档位保持 `disabled / low / high / max`。
   - 新会话和主动选择模型时默认使用 `high`。
   - `max` 继续保留，但只能由用户显式选择，不能作为“未选择”时的兜底值。
   - 已有会话中显式保存的档位不被静默覆盖。

2. **批量文件修改**
   - 启用内置 `ApplyPatch`。
   - 同一文件多处修改、跨文件修改、新增/删除/移动文件优先使用 `ApplyPatch`。
   - 单点小修继续使用 `Edit`；创建或整体覆盖文件继续使用 `Write`。
   - `ApplyPatch` 写入后必须像 `Write`/`Edit` 一样更新 read-file state、memory origin 标记和可持久化元数据。

3. **短会话上下文**
   - VibeCoding 不面向长时间积累的超长上下文；典型任务为 2–3 个用户轮次。
   - 网关继续保留工具调用与工具结果配对，优先限制历史用户轮次，而不是从工具循环中间切断消息。
   - 不新增面向百万级上下文的默认优化；上下文策略以降低首 token 和模型往返为目标。

## 网关约束

- 网关必须显式接收并转发客户端的思考控制字段，至少包括 `reasoning_effort`、`reasoning`、`thinking` 和 `output_config`（存在时）。
- 渠道可以设置固定上限；若渠道不允许 `max`，网关必须显式降级到 `high`，不能让请求静默回落到模型默认值。
- 网关日志至少记录实际转发档位、首 token、上游总耗时、输入/输出/reasoning tokens、缓存命中和重试次数。
- 生产课堂中不得为发布代码改动而中断正在执行的 SSE；需要重启时必须等待活动请求结束。

## 验收

- 新建 `deepseek-flash` 会话的模型选择包含 `reasoningLevel=high`。
- 手动选择 `max` 的既有会话恢复后仍保持 `max`。
- 请求体包含客户端选择的思考字段，并在网关日志中能核对到实际值。
- `ApplyPatch` 出现在主 Agent 工具目录中；一次 patch 可验证并修改多个 hunk。
- ApplyPatch 成功后，立即 Edit 同一文件不出现“未读取/已过期”的误报。
- 典型 2–3 轮课堂任务不因为历史无限增长而扩大首 token 延迟。
